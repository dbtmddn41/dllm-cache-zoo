# First serving target

The proposed first deployment is an online text-generation API using LLaDA-8B-Instruct, Fast-dLLM v1 Prefix, one NVIDIA GPU, BF16, and a deterministic sampler. Optimize one existing batched HTTP path so a product team can enable it in worker configuration. Keep the host integration optional for library users who run their own loop. The target GPU model, traffic mix, quality tolerance, and response deadline depend on the product.

## Start with a host that runs the checkpoint

`dlmserve` is the proposed integration host for this milestone. Its model loader has a BF16 path. Its scheduler groups concurrent requests for denoising, but the pinned revision's KV cache is inert. The worker passes a list of states to `step_batch`, which pads the batch and performs a full-sequence forward. The first feasibility test is to carry a request-owned cache handle through that path and run a mixed-length batch across a block boundary. This is adapter work in the worker. The HTTP API can stay the same. [Model loader](https://github.com/iOptimizeThings/dlmserve/blob/dd3efe743a65e0142627e105e8d18bcc1c33d6cb/dlmserve/models/llada.py#L47-L90) · [Cache implementation](https://github.com/iOptimizeThings/dlmserve/blob/dd3efe743a65e0142627e105e8d18bcc1c33d6cb/dlmserve/kv_cache.py#L25-L69) · [Worker](https://github.com/iOptimizeThings/dlmserve/blob/dd3efe743a65e0142627e105e8d18bcc1c33d6cb/dlmserve/engine.py#L167-L191) · [Batched model call](https://github.com/iOptimizeThings/dlmserve/blob/dd3efe743a65e0142627e105e8d18bcc1c33d6cb/dlmserve/denoise_loop.py#L135-L188)

Use Fast-dLLM as the method reference. Use dInfer as an external performance baseline where checkpoint, precision, sampler, cache settings, and batch size can be matched. dInfer's linked cache driver has a single-prompt path and exposes Prefix and Dual. Compare equivalent generation timings there, and use the same server on both sides of the HTTP comparison. For any future backend with an equivalent native fast path, dispatch to it and measure the overhead of selecting it through the Zoo. [Fast-dLLM Prefix](https://github.com/NVlabs/Fast-dLLM/blob/a9b81e4caa240c8cad4f7dc1889ff4852a0fca5b/v1/llada/generate.py#L157-L193) · [dInfer cache driver](https://github.com/inclusionAI/dInfer/blob/1ffeb961cd258bede74fcf5ca8a416ae6d57b18f/python/dinfer/decoding/generate_cache.py#L68-L123)

## Make the saved work observable

1. **Start with contiguous ranges.** Build the full cache at a block boundary. During refinement, evaluate queries and recompute projections and MLPs for the active block and suffix. Those queries still attend to the cached prefix. Preserve absolute positions and the attention mask for each row. At 2,048 prompt tokens and 256 response positions in blocks of 32, the first pass covers 2,304 positions. On later steps of block one, 256 positions go through the model, while the attention keys still span 2,304. These are shape counts for an example.
2. **Keep cache memory in the worker.** Reuse a bounded GPU buffer or the host's KV allocator. Store logical ranges per live request and map them to physical slots when assembling the batch. Row numbers change as requests enter and leave. Reuse a slot after outstanding device work on it finishes. Account for cache and scratch space at admission. On an unsupported input or an exhausted cache budget, use the native path if it fits and record the reason. Mid-request recovery needs full state recomputation.
3. **Profile the ordinary batched request.** Trace the full rebuild and a later refinement step. Inspect forward shapes, attention time, memory allocation, prefix copies, gather/scatter, and CPU–GPU waits. One concrete target is the reference attention code that concatenates cached and current KV. Try slices, reusable buffers or a kernel that can read the cache layout directly if the trace shows material copying. Recheck end-to-end latency and memory after each change. Introduce a fused kernel or CUDA graph only where measurements justify the extra shape and version constraints. [Reference attention path](https://github.com/NVlabs/Fast-dLLM/blob/a9b81e4caa240c8cad4f7dc1889ff4852a0fca5b/v1/llada/model/modeling_llada.py#L729-L755)

## Decide whether to enable it

| Question | Evidence for the proposed deployment |
| --- | --- |
| Does the implementation reproduce the method? | Compare cache-off to the native host and optimized Prefix to the pinned Prefix reference. Check candidate-position logits with a documented BF16 tolerance and deterministic traces on fixed fixtures. Exercise unequal prompt lengths, padding, multiple blocks, batch reordering, completion, cancellation, and reuse of a freed slot. |
| Will users get acceptable answers? | Pair the same requests and seeds. Report accuracy delta and a paired uncertainty interval against cache-off on a named public set and a task representative of the intended product. Count failures. Agree the acceptable loss with the product team before benchmarking. |
| Does it help the service under load? | Replay the same arrival trace through the normal HTTP endpoint with native cache-off, the adapter disabled, and Prefix enabled. Keep scheduler limits, sampler, other accelerators, and GPU budget fixed. Measure client latency including queueing, deadline goodput (successful in-deadline requests per second per GPU), p50/p95/p99, token throughput, peak memory and errors. Sweep load and report the region where Prefix helps. |
| Can an operator roll it back? | Record the effective method, fallback counts and reasons, and live KV bytes. Exercise cancellation, failure and recovery under load. Demonstrate a cache-off switch for new requests while in-flight work drains. Ship the pinned environment and the commands to replay the traffic. |

For an initial synthetic pilot, use short and long prompts (128 and 2,048 tokens), output budgets of 64 and 256, and client concurrency of 1, 4 and 8. Then replay a representative length mix at fixed arrival rates up to saturation. Record achieved batch sizes, repetitions, request counts, per-request timings and queue growth. Select the deadline and quality tolerance for the intended product before the run. Use deadline goodput per GPU for a capacity-limited service, or p95 latency at fixed offered load for a latency-sensitive one. Choose the primary measure in advance.

Recommend Prefix for a measured workload where the gain over native cache-off exceeds run-to-run variation and quality, tail latency, errors, and memory meet the agreed limits. Publish slower regions too. Roll out to a small share of traffic and switch new requests back to cache-off if those limits are crossed. On the pinned HTTP path the handler awaits generation before returning a streaming response, so the first test reports full response latency. Report time to first committed text if an integration streams incremental output.
