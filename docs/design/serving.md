# Serving integration

A method from the Zoo can also run inside an inference engine that teams already deploy. This page describes how to carry a checked method into such an engine and how to show under load whether it should be enabled. The work follows the installable release in the roadmap. The Zoo builds no server of its own. The engine keeps its HTTP API, scheduler and batching, and a product team enables the method in worker configuration. The target GPU model, traffic mix, quality tolerance, and response deadline depend on the product. [Roadmap](roadmap.md)

## Choose an engine that runs the checkpoint

dInfer is the first candidate. Its README reports batched inference, a vLLM backend for LLaDA and LLaDA-MoE, and an SGLang backend for LLaDA2 with block diffusion decoding. The linked cache driver exposes Prefix and Dual on a single-prompt path. The LLaDA2 README describes its deployment engine as built on dInfer and SGLang. For SDAR, the model README points to JetEngine and LMDeploy. [dInfer backends](https://github.com/inclusionAI/dInfer/blob/1ffeb961cd258bede74fcf5ca8a416ae6d57b18f/README.md#L68-L77) · [dInfer cache driver](https://github.com/inclusionAI/dInfer/blob/1ffeb961cd258bede74fcf5ca8a416ae6d57b18f/python/dinfer/decoding/generate_cache.py#L68-L123) · [LLaDA2 deployment note](https://github.com/inclusionAI/LLaDA2.X/blob/a79832985307bb8ac4a43ceeea54168bfb80f0cf/README.md#L61-L63) · [SDAR inference options](https://github.com/JetAstra/SDAR/blob/4c2749ba103448f45520e8411533710a1e66574d/README.md#L54-L127)

Pick the engine by the checkpoint you serve. The integration is adapter work inside the engine's worker. The first feasibility test is to carry a request-owned cache handle through the batched model call and run a mixed-length batch across a block boundary. A runtime such as vLLM needs its own integration with the runner's per-request block tables and slot mappings. Where an engine already has a native path for the same method, dispatch to it and measure the overhead of selecting it through the Zoo. Use the method's reference implementation and the Zoo's checked policy as the correctness references. [Fast-dLLM Prefix](https://github.com/NVlabs/Fast-dLLM/blob/a9b81e4caa240c8cad4f7dc1889ff4852a0fca5b/v1/llada/generate.py#L157-L193) · [vLLM attention backend](https://docs.vllm.ai/en/stable/api/vllm/v1/attention/backend/) · [Comparison protocol](benchmarking.md)

## Make the saved work observable

1. **Start with contiguous ranges.** Choose a first method whose reusable region is contiguous, such as Fast-dLLM Prefix or the block cache. Build the full cache at a block boundary. During refinement, evaluate queries and recompute projections and MLPs for the active block and suffix. Those queries still attend to the cached prefix. Preserve absolute positions and the attention mask for each row. At 2,048 prompt tokens and 256 response positions in blocks of 32, the first pass covers 2,304 positions. On later steps of block one, 256 positions go through the model, while the attention keys still span 2,304. These are shape counts for a Prefix example.
2. **Keep cache memory in the worker.** Reuse a bounded GPU buffer or the host's KV allocator. Store logical ranges per live request and map them to physical slots when assembling the batch. Row numbers change as requests enter and leave. Reuse a slot after outstanding device work on it finishes. Account for cache and scratch space at admission. On an unsupported input or an exhausted cache budget, use the native path if it fits and record the reason. Mid-request recovery needs full state recomputation.
3. **Profile the ordinary batched request.** Trace the full rebuild and a later refinement step. Inspect forward shapes, attention time, memory allocation, prefix copies, gather/scatter, and CPU–GPU waits. One concrete target is the reference attention code that concatenates cached and current KV. Try slices, reusable buffers or a kernel that can read the cache layout directly if the trace shows material copying. Flash-dLLM publishes a kernel that fuses the projection, rotary embedding and cache write, so compare against it before writing one. Recheck end-to-end latency and memory after each change. Introduce a fused kernel or CUDA graph only where measurements justify the extra shape and version constraints. [Reference attention path](https://github.com/NVlabs/Fast-dLLM/blob/a9b81e4caa240c8cad4f7dc1889ff4852a0fca5b/v1/llada/model/modeling_llada.py#L729-L755) · [Flash-dLLM cache management](https://github.com/VILA-Lab/Flash-dLLM/blob/a667345f5746bb74f060c87bae5997fc3de9710c/README.md#L58-L60)

## Decide whether to enable it

| Question | Evidence for the proposed deployment |
| --- | --- |
| Does the implementation reproduce the method? | Compare cache-off to the engine's stock path and the integrated method to its pinned reference. Check candidate-position logits with a documented BF16 tolerance and deterministic traces on fixed fixtures. Exercise unequal prompt lengths, padding, multiple blocks, batch reordering, completion, cancellation, and reuse of a freed slot. |
| Will users get acceptable answers? | Pair the same requests and seeds. Report accuracy delta and a paired uncertainty interval against cache-off on a named public set and a task representative of the intended product. Count failures. Agree the acceptable loss with the product team before benchmarking. |
| Does it help the service under load? | Replay the same arrival trace through the normal HTTP endpoint with the stock engine, the adapter disabled, and the method enabled. Keep scheduler limits, sampler, other accelerators, and GPU budget fixed. Measure client latency including queueing, deadline goodput (successful in-deadline requests per second per GPU), p50/p95/p99, token throughput, peak memory and errors. Sweep load and report the region where the method helps. |
| Can an operator roll it back? | Record the effective method, fallback counts and reasons, and live KV bytes. Exercise cancellation, failure and recovery under load. Demonstrate a cache-off switch for new requests while in-flight work drains. Ship the pinned environment and the commands to replay the traffic. |

For an initial synthetic pilot, use short and long prompts (128 and 2,048 tokens), output budgets of 64 and 256, and client concurrency of 1, 4 and 8. Then replay a representative length mix at fixed arrival rates up to saturation. Record achieved batch sizes, repetitions, request counts, per-request timings and queue growth. Select the deadline and quality tolerance for the intended product before the run. Use deadline goodput per GPU for a capacity-limited service, or p95 latency at fixed offered load for a latency-sensitive one. Choose the primary measure in advance.

Recommend the method for a measured workload where the gain over the stock engine exceeds run-to-run variation and quality, tail latency, errors, and memory meet the agreed limits. Publish slower regions too. Roll out to a small share of traffic and switch new requests back to cache-off if those limits are crossed. Report full response latency, and report time to first committed text if the engine streams incremental output.
